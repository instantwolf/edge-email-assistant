# MCP Integration — Native vs MCP Tool-Invocation Overhead (Bonus, Phase 7)

**Setup (2026-07-06):** the calendar + task tools were additionally exposed as an
**MCP server from n8n itself** (`workflows/mcp_tools_server.json`, MCP Server Trigger v2,
streamable HTTP at `/mcp/iot26-tools`). A variant agent workflow
(`workflows/email_calendar_assistant_mcp.json`, webhook `/webhook/assistant-mcp`)
consumes them through the **MCP Client Tool** node instead of native n8n tool nodes;
email tools and datetime stay native (scoped swap). Model: qwen3:4b-instruct — same as
the native baseline run `edge-qwen3-4b`. Same 12-interaction protocol, seeded ground
truth, API-verified side effects.

> **Note (2026-07-13):** these numbers are from the qwen3:4b-instruct run above.
> `workflows/email_calendar_assistant_mcp.json` was since changed to default to
> **gemma4:12b-it-qat** (the working model). To reproduce this experiment, set that
> workflow's model back to `qwen3:4b-instruct` so it matches the native baseline. The
> figures here, `eval/results/plots/mcp_overhead.png`, and the report's MCP table
> (`report/frozen_runs.json` → `tab_mcp.tex`) all reflect the original qwen3 run and are
> not regenerated by the standard eval pipeline.

## End-to-end (12 interactions, qwen3:4b-instruct)

| Run | ok | median | max | Notes |
|---|---|---|---|---|
| Native tools (`edge-qwen3-4b`) | 11/12 | 10.0 s | 19.8 s | event on wrong day (Thu), 0 tasks created |
| MCP tools (`edge-qwen3-4b-mcp`) | 11/12 | 7.9 s | 20.8 s | event on the **correct Friday**, 1 well-formed task |

End-to-end differences are dominated by LLM stochasticity, not transport — the MCP run
was *not* slower. (The better write results in the MCP run are run-to-run variance,
not an MCP effect; both failures repeated on #12/list_tasks with HTTP 500.)

## Per-tool-call timings (from n8n execution data)

| Measurement | mean | n |
|---|---|---|
| Native tool nodes in the agent (list_events / create_event / list_tasks) | 319 / 441 / 192 ms | 2 / 1 / 1 |
| MCP **client-observed** (`google_tools_mcp` node, includes transport + server workflow) | **421 ms** | 4 |
| MCP **server-inner** (actual Google tool nodes inside the MCP server workflow) | **400 ms** (312 / 414 / 686 / 187 ms) | 4 |

**MCP transport + orchestration overhead ≈ 21 ms per tool call (~5 %).**

Sanity check: server-inner times match the native-node times for the same operations
(list_events 312 vs 319 ms, create_event 414 vs 441 ms, list_tasks 187 vs 192 ms) —
the underlying Google API work is identical; only the invocation path differs.

## Interpretation

1. In this agent, a tool call costs ~0.2–0.7 s of Google API time while each LLM turn
   costs 1.5–4 s (qwen3) to 10–40 s (gemma4). An extra ~20 ms of MCP transport is
   **noise** — under 0.3 % of a typical interaction.
2. Caveats: small sample (4 MCP calls); client and server share one n8n instance
   (loopback) — a *remote* MCP server would add real network RTT per call; tool
   discovery (initialize + tools/list) happens per agent execution and is not isolated
   in this measurement.
3. Conclusion for the report: **MCP's standardization and modularity come essentially
   for free at this scale** — the agent's tool list is unchanged while the transport
   became interoperable (any MCP-capable client can now use these tools, and the
   tools could be swapped behind the endpoint without touching the agent).
